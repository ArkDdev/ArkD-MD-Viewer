## Что добавлено

### 1. Reading progress bar

Тонкая 2px полоска под TopBar. Слева — терракотовый fill, справа — едва заметная серая "рельса" (`bg-border/40`).

**Поведение:**
- В режиме **view** — отслеживает скролл превью на весь экран
- В режиме **edit (split)** — отслеживает скролл **превью справа** (как ты выбрал)
- В режиме **edit-full** — отслеживает scroll внутри CodeMirror редактора
- На коротких документах (нечего скроллить) — рельса видна, fill = 0%. Layout не прыгает при появлении/исчезновении скроллбара.

Обновляется через `addEventListener('scroll', ..., {passive: true})` плюс `ResizeObserver` — пересчитывает прогресс при изменении контента (например, при смене настроек шрифта/ширины, или при загрузке нового файла).

### 2. Открытие .md → всегда view

Открыл .md файл — режим автоматически переключается на view, независимо от того, в каком режиме был раньше.

**Работает для:**
- Меню → Открыть (Ctrl+O)
- Drag & drop файла на окно
- File association: двойной клик на .md в Explorer

**НЕ работает (специально) для:**
- Watcher silent reload — если файл изменился извне и буфер чистый, mode остаётся прежним
- Conflict modal → "Загрузить обновлённый" — тоже сохраняет режим

### 3. "Новый файл" → пустой буфер + split

Меню → "Новый файл" (Ctrl+N) теперь:
- Очищает буфер до пустого (вместо welcome doc)
- Переключает в split (edit) режим, чтобы сразу можно было печатать

Welcome doc остаётся только при **самом первом запуске** приложения. После первого "Новый файл" к нему уже не вернёшься без перезапуска (это нормально).

## Архитектурные заметки

### `LoadFileOptions` в fileStore

Главное архитектурное решение этой итерации. Раньше `loadFile(path, content)` не различал, **зачем** его зовут — для нового внешнего файла, для silent reload watcher'а, для reload по подтверждению пользователя в conflict modal. Все три случая выглядели одинаково.

Теперь:
```ts
loadFile(path, content, { resetMode: true })   // open / drag / file-assoc
loadFile(path, content)                         // watcher silent reload
loadFile(path, content)                         // conflict reload
reset()                                         // "New file"
```

Плюс счётчик `loadGeneration`, который инкрементируется на любое из этих событий, и `lastLoadOptions` которая запоминает контекст. App.tsx подписан на `loadGeneration` и реагирует на его изменения, читая `lastLoadOptions.kind` чтобы понять что именно произошло.

Это позволяет реагировать на event'ы без двусмысленности: typing в редакторе обновляет `content`, но НЕ инкрементирует `loadGeneration` — App.tsx видит, что это не настоящий load, и не трогает mode.

### SplitView callback для preview scroller

ReadingProgressBar нужен ref на скролл-контейнер. В режимах view и edit-full ref доступен напрямую (Renderer forwardRef, EditorHandle.getScroller). В edit-режиме (split) скролл-контейнер живёт **внутри SplitView** — App не имеет к нему доступа.

Решение: SplitView принимает callback `onPreviewScrollerReady?: (el) => void` и зовёт его в effect'е после монтирования (с `null` при размонтировании). App.tsx устанавливает scrollTarget через этот callback. Это **более инкапсулированный** способ, чем useImperativeHandle — SplitView сам контролирует, что выставлять.

### Welcome doc translation — обход loadFile

В предыдущей итерации i18n я делал live-translate welcome через `loadFile(...)`, что инкрементировало бы loadGeneration и теперь триггерило бы mode reaction. Чтобы этого не было — заменил на прямой `useFileStore.setState({ content, ... })` без bump'а generation. Welcome translate "невидим" для системы режимов.
